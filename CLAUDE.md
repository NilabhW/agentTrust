# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project
Agent Trust Gateway is a signed-mandate verification layer for Razorpay merchants: a human issues a spending mandate to an AI agent, the Verification Gateway checks every purchase request against that mandate's bounds before calling Razorpay's test-mode API, and every decision is written to an append-only audit trail.

Full spec — field-level schemas, endpoint lists, complete per-program test-case checklists: `agent-trust-gateway-buildspec.md` in the repo root. Treat it as the source of truth for scope; don't redesign a program's architecture without updating the spec first.

**Buildspec scope, current as of this writing**: the spec names six programs, and all six are built — 1 (Mandate Service), 2 (Verification Gateway), 3 (Razorpay integration), 4 (Audit Log + UI), 5 (buyer agent), 6 (Groq upsell agent). **Not applied**: a correction to Program 3 calling for headless Checkout automation (Playwright/Puppeteer driving Razorpay's actual Checkout.js) in place of the current webhook-simulator approach (`scripts/simulate-payment.ts`) — Program 3 still uses the simulator. **Applied 2026-09-03**: Program 5 was switched from Gemini to Groq (`GroqAgentClient`) after Gemini's free-tier quota proved too restrictive for reliable demo use — see the buildspec's Program 5 section and the `src/agent/` bullet below for detail. `gemini-client.ts` remains in the codebase, unused but correct.

## Commands
Stack: Node.js + TypeScript, Fastify, better-sqlite3, Vitest.
- Install deps: `npm install`
- Run tests: `npm test` — prefer running a single test file while iterating, e.g. `npx vitest run test/mandate/store.test.ts`, not the full suite
- Run the dev server: `npm run dev` (requires `MANDATE_SIGNING_KEY`; see `.env.example` for all env vars, most of which are optional with sane defaults)
- Typecheck: `npm run typecheck`
- Build / run compiled: `npm run build` then `npm start` (compiles to `dist/`, copies `src/db/schema.sql` alongside it — the schema is read from disk at runtime, not bundled)
- Seed demo data: `npm run seed` (creates 3 demo mandates with real Ed25519 keypairs, private keys written to gitignored `data/demo-keys.json`) then optionally `npm run seed:audit` (sample audit history — requires mandates to exist first; skip this for a clean demo)
- Sign a demo agent request: `npm run sign-demo-request -- <mandate_id> [amount] [category] [item_description]` — prints a ready-to-paste `curl` command against `POST /gateway/verify`
- Simulate a Razorpay payment webhook: `npm run simulate-payment -- <order_id> <amount_rupees> [paid|failed]` — requires `RAZORPAY_WEBHOOK_SECRET` in the environment (matching the running server's); prints a ready-to-paste `curl` command against `POST /razorpay/webhook`
- Run the buyer agent: `npm run buyer-agent -- --canned <clean|step-up|hard-fail>` or `-- --goal "<free text>"` (optionally `--mandate <mandate_id>`) — requires `GROQ_API_KEY` and the dev server already running (`npm run dev`); the agent talks to the Gateway over real HTTP, exactly like any external agent
- If you change `src/db/schema.sql`'s `CHECK` constraints: `src/db/migrate.ts` now detects and rebuilds `audit_log` automatically if its `decision` constraint is missing a value from `DECISIONS` (`src/audit/types.ts`) — this runs on every `buildApp()`/`createDb()` call, so an existing `data/mandates.db` picks up new decision values on next server start with no manual step. This only covers `audit_log.decision` specifically (the constraint this project actually keeps widening); a different `CHECK` change on another table still needs a manual `data/mandates.db*` delete + reseed.

## Architecture

```
Human sets rules → Mandate Service (stores signed spending permissions)
        ↓
AI Agent → Verification Gateway ("the bouncer") → Razorpay Integration (test-mode payments)
        ↓                                    ↓
        └──────────► Audit Log + UI ◄────────┘
```

Eight directories under `src/`, seven of them wired together in `src/app.ts`'s `buildApp()` (the single place that constructs every store/service and registers every route — start here to see how the pieces connect):

- **`src/mandate/`** — issues, signs, stores, and revokes mandates. `canonical.ts` turns a mandate into one deterministic byte string before signing (`signer.ts`, HMAC-SHA256) — required for verification to be stable rather than flaky. Every read re-verifies the stored signature against the row's fields, throwing `MandateIntegrityError` on any mismatch, so direct DB tampering is detected rather than silently trusted. Cumulative spend is *computed* by summing `spend_events` rows, not stored as a counter, to keep the sliding-window semantics correct.
- **`src/gateway/`** — the bounds/gating decision logic; the core of the project. `service.ts`'s `verify()` runs, in order: shape validation → mandate fetch → agent-signature check (`agent-signature.ts`, Ed25519, a *different* scheme from the mandate's own HMAC) → replay check (`replay.ts`, in-memory nonce+timestamp cache, fresh per `buildApp()` call) → `bounds.ts`'s `evaluateBounds()` (a pure function: no DB calls, no clock reads, so it's unit-testable on input/output pairs alone). On `pass`, `MandateStore.incrementSpend()` runs *before* any Razorpay call — see the safety-ordering comment at that call site before ever inserting an `async` step between the bounds check and the increment. On `step_up`, a row goes into `pending_approvals` (`store.ts`) instead; `approveStepUp()` re-fetches and re-validates the mandate (not just the approval) before granting it, since a step-up can sit pending for minutes and revocation must stop the money even mid-flight.
- **`src/razorpay/`** — thin wrapper around Razorpay's real test-mode Orders API, only ever called by the Gateway, never reachable directly by an agent. `webhook-signature.ts` is a *third*, separate HMAC scheme (Razorpay's webhook secret, raw-body message) — see "Why three signature schemes" below. `orders-store.ts`'s `orders` table exists because Razorpay's webhooks carry only `order_id`/`payment_id`, never `mandate_id`; it's both the attribution source and the idempotency guard for webhook processing. `webhook-service.ts` deliberately lets a later `order.paid` win over an earlier `payment.failed` on the same order (Razorpay fires `payment.failed` per failed *attempt*, not per order — a retried payment can still succeed).
- **`src/audit/`** — append-only `audit_log`, enforced by DB-level `BEFORE UPDATE`/`BEFORE DELETE` triggers that `RAISE(ABORT, ...)`, not just application-level convention. `AuditStore.writeEntry()`/`list()` (cursor pagination via `before_id`, not `created_at`, since timestamps can collide).
- **`src/ui/`** — serves the single static dashboard page (`public/index.html`, no build step — edits take effect on next page load).
- **`src/demo/`** — convenience routes (`GET /demo/agents`, `POST /demo/purchase`, `POST /demo/settle`) that exist only so the dashboard can be clicked through without a terminal. They read demo private keys straight off disk (`data/demo-keys.json`) and sign/settle on the agent's behalf server-side — **not a template for a real integration**; a real agent holds and uses its own key, and a real payment settlement always goes through webhook signature verification. These routes fail closed (empty/400) if `data/demo-keys.json` doesn't exist.
- **`src/agent/`** — the Program 5 buyer agent. Not part of `buildApp()`/not a Fastify route at all: it's a standalone client, invoked via `scripts/run-buyer-agent.ts`, that talks to an already-running Gateway over **real HTTP** (unlike `src/demo/`'s in-process shortcuts) — per the buildspec, "exactly like any external agent would." `catalog.ts` is a static mock item list (also reused by `src/upsell/`, cross-module import rather than duplicated); `gemini-client.ts` is a thin `fetch`-based wrapper around Gemini's REST `generateContent` endpoint (mirrors `RazorpayClient`'s shape: injectable `fetchImpl`, `AbortSignal.timeout()`-bounded, API key via header not query string) — **no longer the default path** (see below); `groq-agent-client.ts`'s `GroqAgentClient` is what `scripts/run-buyer-agent.ts` actually constructs now, implementing the exact same `ContentGenerator` interface (`generateContent(input) -> result`) that `loop.ts` depends on, so `loop.ts` itself needed zero changes for the swap — it translates Gemini's `contents`/`parts`/`functionCall`/`functionResponse` wire shape to and from Groq's OpenAI-compatible `messages`/`tool_calls` shape, re-deriving synthetic `tool_call` ids by walking the replayed conversation in the same order every call (stateless but consistent, since `functionCall`/`functionResponse` parts always appear paired in the order `loop.ts` produces them). `tools.ts` declares `browse_catalog`/`submit_purchase` and implements them — `submit_purchase` reuses `gateway/agent-signature.ts`'s `signAgentRequest()` unmodified and is the *only* path to a purchase, with no import of `src/razorpay/` anywhere in this module; `loop.ts` is the actual agentic loop (call the model → execute any tool calls → feed results back → repeat until the model stops calling tools or a turn cap is hit), deliberately telling the agent its allowed categories but not its numeric spending caps, so it has to discover its own limits by trying — same as a real agent would. The agent's reasoning transcript is printed live to the terminal, not written into `audit_log` (that table's `decision` enum means "a Gateway/Razorpay decision," not free-text reasoning) — the intended demo is the terminal (agent reasoning) and the dashboard (Gateway enforcement) side by side.
- **`src/upsell/`** — the Program 6 Groq bounded upsell agent. Unlike Program 5, this *is* wired into `buildApp()`/the Gateway's own decision path. `headroom.ts` is pure (`calculateHeadroom()`, `filterCandidates()` — the latter reuses `agent/catalog.ts`'s `getCatalog()`) and pre-filters to in-scope, affordable items **before** the model ever sees them, so it can't suggest something the Gateway would reject anyway. `groq-client.ts` mirrors `GeminiClient`/`GroqAgentClient`'s shape against Groq's OpenAI-compatible chat-completions endpoint, with a deliberately tight timeout (5s default, vs. Program 5's 20s) since this call must never add noticeable latency — a separate client from `agent/groq-agent-client.ts` because the two want different models (JSON-mode suggestion vs. multi-turn tool-calling) even though both call Groq. `service.ts`'s `UpsellService.suggestUpsell()` also re-validates the model's chosen `item_id` is actually in the pre-filtered set (defense-in-depth against a hallucinated pick) before persisting anything; its `accept()` re-signs a fresh purchase via the mandate's demo key (`demo/keys.ts`, extracted from `src/demo/routes.ts` for this exact reuse) and calls `GatewayService.verify()` **from the top, no shortcuts** — a completely fresh bounds check, so spend consumed between suggestion and acceptance is genuinely caught, not assumed safe. **Trigger wiring**: `gateway/service.ts`'s shared `tryCreateOrder()` (used by both the direct-pass path and the step-up-approval path) fires `upsellService.suggestUpsell(...)` **without awaiting it** right after writing `order_created`, so a slow or failed Groq call can never delay or break the purchase response that triggered it (regression-tested in `test/gateway/service.upsell.test.ts`, which asserts the HTTP response returns before a deliberately slow Groq call resolves). **Circular-dependency note**: `UpsellService` needs a constructed `GatewayService` (for `accept()`), and `GatewayService` needs to call into `UpsellService` (to trigger suggestions) — `gateway/service.ts` breaks this by declaring its own local structural `UpsellTrigger` interface (never importing `UpsellService` directly) plus a post-construction `setUpsellService()` setter that `app.ts` calls once both are built, exactly mirroring how `agent/loop.ts` avoids importing any concrete content-generator class (`GeminiClient` or `GroqAgentClient`) behind its `ContentGenerator` interface.

### Why three signature schemes
| Module | Protects | Algorithm / key |
|---|---|---|
| `mandate/signer.ts` | A mandate's terms haven't been edited since creation | HMAC-SHA256, `MANDATE_SIGNING_KEY` |
| `gateway/agent-signature.ts` | A purchase request really came from the agent holding that mandate's key | Ed25519, per-mandate keypair |
| `razorpay/webhook-signature.ts` | A webhook claiming to be from Razorpay really is | HMAC-SHA256, `RAZORPAY_WEBHOOK_SECRET` |

Each protects a different trust relationship with a different key — never reuse one scheme's verification code for another. `src/upsell/`'s `accept()` flow deliberately reuses `gateway/agent-signature.ts`'s scheme rather than adding a fourth — it's the same "sign a purchase server-side on a demo mandate's behalf" trust level as `src/demo/routes.ts`, not a new kind of trust.

### Razorpay and Groq wiring are both fully optional
`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` and `GROQ_API_KEY` are all plain optional env vars, following the identical pattern. `buildApp()` only constructs a `RazorpayClient` when the Razorpay key id/secret are both present, and only a `GroqClient`/`UpsellService` when `GROQ_API_KEY` is present; routes (`POST /razorpay/webhook`, `GET|POST /upsell/*`) are only *registered* when their key is present (unregistered, not just disabled — hitting them 404s). With nothing set, the Gateway still fully enforces every rule; `order_id` stays `null`, no `order_created`/`payment_captured`/`payment_failed`/`upsell_*` entries are written. Both are regression-tested guarantees (`test/gateway/service.razorpay.test.ts`, `test/gateway/service.upsell.test.ts`), not just assumptions.

**Security review findings addressed this phase** (run via the `security-reviewer` subagent against the full Program 6 diff): the reviewer reproduced a real bug against the actual local dev database, not just in theory — `audit_log`'s `decision` `CHECK` constraint had been widened in `schema.sql` for this phase's three new values, but `CREATE TABLE IF NOT EXISTS` is a no-op on an already-existing table, so the constraint on disk was still the old one. Every `upsell_suggested`/`upsell_accepted`/`upsell_declined` write on that database threw, and because the trigger site is deliberately fire-and-forget (`gateway/service.ts`'s `tryCreateOrder()`, `.catch(() => {})`), the failure was swallowed silently — leaving a live, actionable "suggested" row with a working Accept button and zero audit trail, the exact append-only guarantee this project treats as load-bearing. Fixed at the root: `src/db/migrate.ts` now detects (via `sqlite_master`) whether `audit_log`'s on-disk constraint is missing any value from `DECISIONS` and, if so, rebuilds the table with the current constraint in place, preserving all existing rows and triggers — sourced from `DECISIONS` itself, not a second hardcoded list, so it stays correct as future decisions are added. Hardened `UpsellService.suggestUpsell()` to write the audit entry *before* persisting the `upsells` row (so a storage failure of any kind fails toward "phantom log entry, nothing actionable" rather than the reverse), and the fire-and-forget `.catch()` now at least `console.error`s instead of going fully silent. Separately, the reviewer traced a real (bounded, not exploitable for money movement) prompt-injection surface: `purchasedItemName` (the agent-signed, attacker-influenceable `item_description` field) was interpolated unsanitized into the Groq prompt, and Groq's `reason` was persisted and displayed to the operator next to the Accept button with no length cap — an agent could author persuasive or malformed text an operator reads while deciding whether to approve additional spend. `item_id`/`category`/`amount` were never at risk (always sourced from the pre-filtered catalog, never from the model), but `reason` was model/agent-influenced text reaching a human decision-maker unbounded. Fixed: both the prompt input and the persisted/audited `reason` are now stripped of newlines/control characters and length-capped, and the Groq request now sets `max_completion_tokens` to bound response size defensively. Also fixed: the dashboard silently refreshed after an Accept click with no feedback if the resulting fresh `verify()` call turned out `hard_fail`/`step_up` (e.g. headroom consumed between suggestion and acceptance) — it now surfaces that outcome instead of leaving the operator to notice it in the audit table.

## Design principles (the "why" behind the rules below)
- **Signing is the trust boundary.** Mandates are cryptographically signed so the Gateway can verify authenticity without trusting the caller; agent requests are separately signed with a per-mandate keypair issued at mandate-creation time.
- **Step-up vs. hard-fail is a deliberate policy split, not a default.** Only "would exceed cumulative cap" gets a human-in-the-loop retry path. Bad signature, expired mandate, revoked mandate, and out-of-scope category are all immediate hard fails. Don't collapse these into each other without flagging it explicitly.
- **Audit logging is a functional requirement, tested directly** — not instrumentation bolted on after the fact. Every decision branch must produce exactly one correctly-reasoned entry, and the log must be genuinely append-only.
- **Bounds-checking is a pure function**, by design, for testability: no DB calls, no Razorpay calls inside the decision function itself.

## Code style
- Normalize all Gateway decisions to `{decision: pass | hard_fail | step_up, reason}` — every caller branches on this shape, not on ad-hoc booleans.
- All signing and signature-verification code lives in one module per scheme. Never inline a signature check elsewhere.

## Workflow rules
- **Before writing any Razorpay integration code, fetch Razorpay's current test-mode API docs.** Field names and endpoint shapes drift — this is the highest-risk area for silent bugs, don't rely on memorized specifics.
- Every Gateway decision branch (pass, hard-fail, step-up-requested, step-up-approved, step-up-denied, step-up-timeout) must write exactly one audit entry. Adding a new branch means adding its test case to the spec before implementing it, and adding the value to both `DECISIONS` (`src/audit/types.ts`) and the `CHECK` constraint (`src/db/schema.sql`).
- The audit log is append-only. Never add an UPDATE or DELETE path — fix forward with a new entry, not by editing history.
- IMPORTANT: never hardcode Razorpay API keys, webhook secrets, or signing keys. Env vars only. Never print them in logs, error messages, or commits.
- Run the `security-reviewer` subagent (`.claude/agents/security-reviewer.md`) after any change to signing logic, bounds-checking, or the webhook handler — before merging, not after.
- After implementing a program, run its test cases from the build spec before starting the next one.

## Testing
- Test cases for all four programs live in `agent-trust-gateway-buildspec.md` — treat that list as acceptance criteria, not a suggestion.
- Don't consider the Verification Gateway "done" on happy-path tests alone — the replay, expiry, revocation, and step-up test cases are the ones that actually matter for this project's premise.
- Test files mirror source 1:1: `test/<module>/<layer>.test.ts`. Every source file's test is written and confirmed failing before implementation (this repo is built test-first throughout).

## Known, accepted limitations
Deliberate, documented trade-offs — not bugs to silently fix:
1. `POST /mandates` has no authentication — anyone reaching the service can mint a mandate for any `user_id`. A real fix requires a whole-system auth decision (operator sessions vs. API keys) that hasn't been made yet.
2. The replay-protection nonce cache is in-memory and per-process (per the buildspec's explicit hackathon-stage allowance) — resets on restart, isn't shared across instances behind a load balancer.
3. Spend is incremented *before* `create_order()` is called (Program 3's call must sit after `incrementSpend()`, never between the bounds check and the increment — see the safety-ordering comment in `gateway/service.ts`). If `create_order()` then fails, the spend stays committed even though no order exists — visible in the audit trail as `payment_failed`, not automatically reversed.
4. There is no request-level idempotency key beyond `ReplayGuard`'s nonce, which only catches a byte-identical resubmission. A client-side retry after a timeout carries a fresh nonce and signature, so it's indistinguishable from a genuinely new purchase and can double-increment spend for what the agent considers one purchase. Closing this needs an agent-supplied idempotency key threaded through the signed request schema — a protocol change, not done.
5. **New in Phase 7**: an agent can still influence the short `reason` text an operator reads next to an upsell's Accept button (via the agent-controlled `item_description` field feeding the Groq prompt) — now length-capped and stripped of control characters, but not eliminated as an information channel. It cannot affect what gets bought (`item_id`/`category`/`amount` always come from the pre-filtered catalog, never the model) or bypass any bound (`accept()` re-verifies from scratch), so the residual risk is misleading operator-facing text, not unauthorized spend.

## Implementation history
Built in seven phases, each test-first: (1) Mandate Service, (2) Audit Log + minimal UI (built ahead of the Gateway so every later program could log from day one), (3) Verification Gateway, (4) Razorpay test-mode integration, (5) interactive demo UI (`src/demo/`, real Approve/Deny buttons, redesigned dashboard), (6) buyer agent (`src/agent/`, Program 5 — a real model making purchasing decisions against the already-built infrastructure, over real HTTP; originally Gemini, switched to Groq on 2026-09-03 after Gemini's free-tier quota proved unreliable for demo use — see the buildspec's Program 5 section), (7) Groq upsell agent (`src/upsell/`, Program 6 — wired directly into the Gateway's decision path, fire-and-forget). A `security-reviewer` pass ran on phases that touched signing/bounds/webhook code (1–4, 7); phase 6 reuses existing signing code unmodified and touches neither bounds-checking nor the webhook handler, so it was skipped there. The Program 5 provider swap likewise reuses existing signing code unmodified and touches neither bounds-checking nor the webhook handler. `README.md` covers the problem/solution/architecture for an external reader.
